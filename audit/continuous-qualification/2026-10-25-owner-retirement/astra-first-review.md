## Runtime assessment

**SQL integrity and uncertainty.** I traced Lane submission, preparation, receive/drain, item accounting, failure handlers, connection loss and recovery through the full `src/session.cpp`, not only the PR diff. Accepted work owns its parameters and SQL. Dispatch is conservatively marked before the libpq send; interrupted dispatched work without confirmation becomes UNCERTAIN. Recovery settles already queued work rather than replaying it on a new session. Preparation failure precedes execution and does not represent an executed write. Extended protocol, local command restrictions and transaction-state reconciliation are consistent with the single-command contract. Stream delivery after definitive SQL confirmation preserves a confirmed item even if the job fails locally. Within transactions, successful statements remain provisional until COMMIT; neither cancellation nor session loss promises a confirmed rollback.

**Transactions and reservations.** Engine reserves finishing capacity and marks a transaction ending before accepting its finish job; enqueue rejection removes that marker. Worker failure poisons live transaction state, rollback-to explicitly clears it, and rejected COMMIT reconciles physical ownership or closes the session. Idle transaction expiry does not pretend to complete an application finish: callers still need the documented finish/connection-retirement cleanup. I found no new incorrect release or opportunity to silently replay a transaction in these paths.

**Owner retirement changes.** `src/engine.cpp:457-478` now traverses existing registries, closes owned lanes, erases staging and marks existing jobs without allocating an owner tombstone. `Job::owner_unloaded` is main-thread bookkeeping; workers do not read it. Clearing callback descriptors on unload does not race with worker SQL/result fields. Terminal status can precede completion-queue insertion, but shared ownership remains with the worker and subsequently the intrusive queue. `src/engine.cpp:501-505` removes finish markers independently of connection/job registry survival; `src/engine.cpp:554-561` covers terminal unloaded jobs retired before queue publication. Handle non-reuse makes repeated erasure idempotent rather than capable of erasing a newer transaction with the same ID.

**Concurrency and lifetime.** Engine registries and callback metadata remain confined to the owning thread. Lane exclusively owns its PGconn. Results and terminal metadata are published before atomic terminal status; native reads require terminal status except explicitly immutable or separately synchronized fields. CompletionQueue keeps accepted Job ownership without a terminal allocation and drains abandoned chains iteratively. Engine closes and joins lanes before completion queue/diagnostics destruction. Stream uses one pending block, one current main-thread block and one worker block; main-thread advancement uses try-lock, while producer waits observe cancel/stop/deadline. Poll reserves output capacity before consuming deliveries, preserving retry on allocation failure.

**Native and callback boundaries.** Full Component/native review found per-cell AMX address validation, copied bounded callback arguments, whole-output preflight, a noexcept native boundary and terminal gating for worker data. Callback delivery moves its descriptor before Pawn execution and checks owner survival before restoring the frame. Later deliveries revalidate handles after earlier callbacks can close them. Unload/reload uses distinct owner generations. The account example checks job identity, player connectivity, token and state; tokens survive GMX through a server counter and fail closed at exhaustion. Custom callbacks similarly reject stale player-slot identities. These tutorials are not a general authorization or durable transaction service.

**Staging, files, types and resources.** I reviewed statement snapshots and batch transfer rollback, parameter/array/BYTEA/UTF-8 conversion, the SQL-section lexer/capture path, SQL reader, configuration, diagnostics and file writer. Staging allocation occurs before acceptance, and rejected execute restores the original batch. SQL reads enforce a bounded probe and reject failed/partial input. Named sections are captured before their job's dispatch; ordinary heterogeneous whole-file operations retain their documented per-operation behavior. Supported Pawn configuration bounds arithmetic and counts; positive handles do not wrap/recycle. Logs use fixed numeric queues, bounded files and explicit dropped/failure accounting; short writes disable the destination rather than spin. Retained results require explicit close; unload collects abandoned owner resources.

The review also examined account, custom-callback, saving, transfer and unload examples, relevant transaction/callback/design contracts, and the current workflow's exact-source checkout, platform dependency acquisition and qualification paths. Runtime review is broader than the two new fixes; it is not a claim of formal verification or exhaustive testing of every external dependency.

## Regression assessment and nonblocking gaps

No new defect is asserted in this section. These are specific opportunities to strengthen evidence.

1. **Post-confirmation allocation failure (low-priority coverage gap).** `src/session.cpp:400` establishes SQL confirmation before `job.results.push_back` at lines 561 and 661. The catch-all path should keep the current item confirmed/completed, report local internal failure, drop the session and avoid replay even if a result cannot be retained. Add a focused allocation checkpoint at each result-vector insertion, including COMMIT and an earlier confirmed batch prefix. Assert item statuses/count, missing-payload behavior, connection recovery and exactly one database effect. This is consistent with the present contract; no incorrect result was reproduced here.

2. **Publication-order coverage (low-priority extension).** `tests/transaction_retirement.cpp` exercises the actual poll with six controlled snapshots: both finish kinds with a missing connection, a retired job, and terminal status before queue publication. It checks unrelated markers and immutable terminal metadata. These are valid reachable-state unit tests, but they do not force a live worker interleaving. An optional deterministic worker barrier at terminal publication in a test-only translation unit could complement them, asserting one delivery/retirement across unload and connection reaping. Existing tests should not be described as that stronger experiment.

3. **Allocation-denial boundary.** `tests/unload_allocation.cpp` includes an active denial control, repeated empty unloads and real active/queued/terminal owner resources. Its active-query observer avoids assuming that a running status means dispatch. It verifies no replay, descriptor suppression, resource retirement and another owner's unaffected work. TSan intentionally retains allocator interceptors and demonstrates lifecycle behavior, not global allocator denial. The replacement covers the ordinary allocations used by this path; it is not an assertion that all possible external allocators have been exhausted.

High-water/sample data is not a proof of no leak. Streams bound retained blocks, not arbitrary server row size.

The writer's bounded queue does not establish a bounded duration for a stalled filesystem syscall. These are already documented deployment limitations, not newly reproduced defects.
- TSan instruments project code, not all libpq/OpenSSL internals. Full descriptor exhaustion is not configured under every sanitizer. Finite wire faults, native doubles, Pawn compilation and bounded real clients do not cover every schedule, corrupted VM, provider or graphical client.
- SQL files and service profiles are operator-managed. Administrator symlink races and hostile administrator-authored SQL remain outside the confinement promise. Hash inventories establish byte identity, not hermetic compilation, signed provenance or indefinite artifact retention.
