## Correction and SQL integrity

The old defect was concrete: a failed transaction's requested COMMIT is physically replaced with ROLLBACK; successful ROLLBACK set the generic confirmation flag, but that flag was reset only after retaining its result. An insertion exception therefore marked the never-dispatched COMMIT confirmed/completed even though the job remained FAILED/INTERNAL. This was false per-item confirmation, not demonstrated COMMIT execution or automatic replay.

At `src/session.cpp:663`, the new conditional clears both `sql_confirmed_` and `query_dispatched_` immediately after successful fallback ROLLBACK and before the checkpoint/result insertion at lines 669-670. Thus catch-all handling cannot convert that physical ROLLBACK into requested-COMMIT confirmation. Successful non-fallback COMMIT and ROLLBACK retain their confirmation flags. If allocation fails, the generic handler preserves confirmed current-item accounting where appropriate, drops the connection, and makes the local payload failure explicit. On rejected COMMIT it instead keeps completed zero and the requested item failed. No retry is introduced.

The named exception seams at lines 284, 562 and 669 are production no-ops. `tests/confirmed_allocation.cpp` includes the actual Lane implementation with test-only injection, leaves sanitizer allocator interceptors intact, and counts exactly one injected exception at the selected occurrence. Its seven cases cover ordinary write, streamed write, confirmed trailing-block delivery failure, second item of a three-item batch, COMMIT, ROLLBACK and rejected COMMIT. Assertions include terminal delivery count, structured failure, confirmed prefix and undispatched suffix, absent current payload with retained previous payload/stream block, independently observed database count/value/effect, physical command count, single session recovery, explicit fresh SQL and transaction reservation reuse. The stream-delivery case deliberately leaves the first full block pending until the confirmed trailing partial block times out. This is a meaningful distinction from an unconfirmed mid-stream interruption.

The retained `restore-before.patch` moves the reset back across only the affected insertion and preserves test seams. The checkpoint records the original negative `completed=1 results=0 item0=1` and corrected `completed=0 results=0 item0=2`. That historical failed experiment remains a failure. I inspected the patch and test logic but did not independently re-execute either C++ result.

Related paths remain conservative: confirmation follows definitive drain and healthy connection; dispatch is marked before libpq send; incomplete dispatched commands become uncertain; recovery settles existing queued work instead of replaying it. Prepared-statement refresh happens on a future explicit execution. Each batch item resets dispatch/confirmation flags. Confirmed transaction statements remain provisional until COMMIT. Closing a session after local failure does not promise that an uncertain write was undone.

## Ownership, concurrency and callbacks

`Engine::submit` allocates item metadata and registry ownership before enqueue and removes registry insertion on rejection. Statement execution restores staged batch ownership when submission fails. Finish admission reserves capacity and installs the ending marker before network acceptance; rejection removes it. Worker transaction ownership is reconciled on finish rejection or session drop. Poll releases finish reservations and ending markers independently of connection/job registry survival. These properties still align with the correction's forced recovery.

`CompletionQueue` keeps shared ownership with an intrusive link under its mutex and destroys abandoned chains iteratively. Worker data is written before atomic terminal status; terminal native access checks status. The reviewed code keeps callback descriptors and owner-unloaded bookkeeping on the main thread. Engine shutdown closes and joins lanes before their shared dependencies disappear. Stream retention uses worker, pending and main-thread blocks; producer waits observe stop/cancel/deadline, while main-thread `next()` uses try-lock. These checks did not reveal a new race or lost terminal delivery in the inspected paths; they are source reasoning, not an independent schedule exploration.

Component delivery moves custom arguments before Pawn execution and revalidates each job after earlier callbacks may have closed it. It checks owner survival before restoring the AMX frame after execution. Native address/output helpers validate cells and complete writes, copy input, gate terminal fields and catch exceptions at the native boundary. Account/custom callbacks bind player slot, session token and pending job; the account token counter survives GMX and fails closed at its bound. These examples' session checks do not establish general application authorization or durable distributed transaction guarantees.

The earlier nonblocking publication-order coverage observation remains: snapshot-based retirement tests are not a forced live-worker publication interleaving. A deterministic test-only worker barrier could strengthen that evidence. It is not a confirmed defect or a new prerequisite to preparing infrastructure.
